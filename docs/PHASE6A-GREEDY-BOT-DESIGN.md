# Phase 6：无质疑模式贪心机器人设计

## 阶段目标

Phase 6 的目标是在《雷霆 UNOplus》中加入服务端控制的自动出牌机器人。机器人用于补足人数、方便本地试玩和演示，也为后续公开试玩降低组局门槛。

本阶段先完成机器人系统设计，后续实现时必须保持现有架构边界：

1. 服务端仍然是唯一权威状态。
2. `uno-core` 仍然是唯一规则归属地。
3. 前端只负责大厅按钮、机器人标签和对战展示，不负责替机器人判断合法出牌。
4. 机器人只能读取自己的手牌、公开牌桌状态、其他玩家手牌数量和公开事件，不能读取真人玩家手牌。

## 功能范围

第一版机器人只支持无质疑模式：

```txt
mode === "no-challenge"
```

支持内容：

1. 房主在大厅添加机器人。
2. 机器人自动加入等待房间并占用座位。
3. 机器人自动准备。
4. 满足 3 人开局要求后，房主可以开始游戏。
5. 轮到机器人时，机器人等待 3 秒后自动行动。
6. 机器人能自动出单牌、对子、顺子、同色丢弃、黑牌、加牌牌。
7. 机器人能处理摸牌、刚摸牌是否打出、加牌链结算、罚抽结算。
8. 机器人剩 1 张牌时有 80% 概率喊 UNO，20% 概率忘记喊 UNO。

暂不支持：

1. 有质疑模式机器人。
2. 机器人主动质疑。
3. 机器人难度等级。
4. 机器人聊天、表情或个性化头像。
5. 开局后继续添加机器人。

## 总体架构

机器人应作为 `apps/game-server` 内部能力实现，而不是模拟一个浏览器客户端。

建议新增目录：

```txt
apps/game-server/src/bot/
├── botScheduler.ts
├── greedyBot.ts
├── botCandidates.ts
└── botScoring.ts
```

模块职责：

1. `botScheduler.ts`：管理机器人 3 秒思考定时器，避免重复调度。
2. `greedyBot.ts`：机器人决策入口，读取当前局面并输出最终动作。
3. `botCandidates.ts`：根据 `uno-core` 合法性规则生成候选动作。
4. `botScoring.ts`：对候选动作做贪心评分和排序。

服务端流程：

```txt
房主点击添加机器人
客户端发送 add-bot
服务端校验房间和房主权限
RoomManager 创建机器人玩家
广播 room-state
房主开始游戏
任意命令成功后检查当前玩家
如果当前玩家是机器人，设置 3 秒定时器
3 秒后重新读取最新局面
生成候选动作
计算最高分动作
服务端内部执行 GameCommand
广播 events 和 snapshot
继续检查是否轮到机器人
```

## 数据模型设计

### 服务端玩家

`ServerRoomPlayer` 增加机器人字段：

```ts
interface ServerRoomPlayer {
  isBot: boolean;
  botProfile?: {
    strategy: "greedy-v1";
    forgetUnoRate: 0.2;
  };
}
```

真人玩家：

```ts
isBot: false
```

机器人玩家：

```ts
isBot: true
connectionId: null
connected: true
hasLeftRoom: false
isReady: true
botProfile: {
  strategy: "greedy-v1",
  forgetUnoRate: 0.2
}
```

### 共享快照

`RoomSnapshotPlayer` 建议增加：

```ts
isBot: boolean;
```

前端用它展示机器人标签。对战快照中的 `self/opponents` 也可增加 `isBot`，用于显示“思考中...”和机器人身份。

## 协议设计

新增客户端消息：

```ts
interface ClientAddBotMessage {
  protocolVersion: typeof PROTOCOL_VERSION;
  type: "add-bot";
  requestId: RequestId;
  roomId: RoomId;
  playerId: PlayerId;
  timestampMs: UnixMs;
}
```

服务端校验：

1. 房间存在。
2. 发起玩家是房主。
3. 房间处于 waiting。
4. 房间模式是 `no-challenge`。
5. 房间人数小于 8。

失败提示建议：

```txt
只有房主可以添加机器人
只有无质疑模式可以添加机器人
房间已满
对局开始后不能添加机器人
```

## 大厅 UI 设计

在大厅房间面板的操作区增加按钮：

```txt
添加机器人
```

启用条件：

1. 当前玩家是房主。
2. 当前玩家已经在房间内。
3. 房间状态是等待中。
4. 房间模式是无质疑。
5. 玩家总数小于 8。

禁用时使用 `title` 提示原因。

玩家列表中机器人显示：

```txt
雷霆bot1
机器人
已准备
```

UI 建议：

1. 机器人玩家卡片加蓝色 `BOT` 或 `机器人` 标签。
2. 机器人永远显示已准备。
3. 机器人不显示断线状态。
4. 机器人使用现有头像池，后续再替换专用头像。

## 对战 UI 设计

对战页中机器人和真人一样出现在座位上，但需要额外显示身份。

建议：

1. 头像框显示机器人昵称。
2. 小标签显示 `机器人`。
3. 轮到机器人时状态显示 `思考中...`。
4. 日志可以追加：

```txt
雷霆bot1 正在思考...
雷霆bot1 打出了 蓝5
雷霆bot1 忘记喊 UNO
```

日志只作为体验增强，不参与规则。

## 机器人行动节奏

机器人必须模拟思考 3 秒：

```ts
const BOT_THINK_MS = 3000;
```

触发时机：

1. 开局后当前玩家是机器人。
2. 真人操作后轮到机器人。
3. 机器人摸牌后进入刚摸牌决策窗口。
4. 机器人被加牌链或罚抽压力指向。
5. 房主继续游戏后轮到机器人。

安全要求：

1. 定时器结束后必须重新检查 `room.gameState.currentPlayerId`。
2. 如果当前玩家已经不是该机器人，取消动作。
3. 如果房间已结束、机器人已淘汰、机器人已胜利或玩家离房，取消动作。
4. 每个房间同一时间只允许一个机器人思考定时器。
5. 机器人动作失败最多重算一次，避免死循环。

## 候选动作生成

机器人不直接挑一张牌，而是生成所有候选动作，再评分。

候选动作结构：

```ts
interface BotCandidateAction {
  type:
    | "play-single"
    | "play-sequence"
    | "play-multiple"
    | "play-discard-same-color"
    | "draw-card"
    | "resolve-draw-stack"
    | "resolve-draw-until-color"
    | "keep-drawn-card";
  cardId?: string;
  cardIds?: string[];
  declaredColor?: CardColor;
  targetPlayerId?: PlayerId;
  score: number;
  reasons: string[];
}
```

候选来源：

1. 所有合法单张出牌。
2. 所有合法对子或多张同色同数字组合。
3. 所有合法顺子，至少 5 张数字牌。
4. 所有合法同色丢弃组合。
5. 所有合法黑牌及其声明颜色。
6. 加牌链中的合法叠加牌。
7. 无法叠加时的 `resolve-draw-stack`。
8. 罚抽压力中的罚抽牌或 `resolve-draw-until-color`。
9. 无牌可出时的 `draw-card`。
10. 刚摸牌窗口中的 `play-card` 或 `keep-drawn-card`。

合法性必须复用 `uno-core`：

1. 单张出牌用 `canPlayCard`。
2. 加牌链用 `canStackDrawCard`。
3. 顺子、对子、同色丢弃用 `uno-core` 现有组合规则或抽出的共享判断。
4. 最终执行仍由 `applyCommand` 校验一次。

## 贪心评分模型

机器人使用贪心算法：只评估当前局面，不做多层搜索。

总分可以理解为：

```txt
总分 =
  减牌分
+ 威胁压制分
+ 颜色控制分
+ 特殊收益分
- 关键牌保留成本
- 风险成本
```

### 减牌分

```txt
出牌数量 * 100
```

示例：

1. 单张：+100。
2. 对子两张：+200。
3. 顺子五张：+500。
4. 同色丢弃带出四张：+400。

### 手牌压力

手牌越多越要积极减牌。

```txt
handCount >= 15：组合出牌额外 +120
handCount >= 10：组合出牌额外 +70
handCount <= 4：关键牌保留成本提高
```

### 胜利和 UNO

```txt
出完所有手牌：+10000
出牌后剩 1 张：+1200
出牌后剩 2 张：+350
```

出牌后剩 1 张时：

```txt
80% 发送 say-uno
20% 不发送 say-uno
```

随机数需要可注入，方便测试稳定复现。

### 下家威胁

当前方向上的下家越接近胜利，压制牌越值钱。

```txt
下家 handCount == 1：禁 / 加牌 / 罚抽 / 有利反转 +500
下家 handCount == 2：禁 / 加牌 / 罚抽 / 有利反转 +300
下家 handCount <= 4：压制牌 +150
```

反转需要额外判断方向收益：

```txt
反转能避开低手牌下家：+250
反转会让低手牌上家更快行动：-250
```

### 加牌压力

基础压制分：

```txt
普通 +2：+120
普通 +4：+180
黑色反转 +4：+260
变色 +6：+420
变色 +10：+700
```

保留策略：

```txt
有当前颜色可出且下家不危险：+6 额外 -220
有当前颜色可出且下家不危险：+10 额外 -360
没有当前颜色可出：取消 +6 / +10 保留扣分
下家 handCount <= 2：取消 +6 / +10 保留扣分并加威胁压制分
正在加牌链中且不打会摸很多：取消高价值黑牌保留扣分
```

### 颜色控制

机器人应该尽量把颜色切到自己的优势色。

颜色评分：

```txt
该颜色手牌数量 * 40
该颜色对子潜力 * 30
该颜色顺子潜力 * 40
该颜色技能牌数量 * 20
当前颜色额外 +20
```

黑牌声明颜色时，选择颜色评分最高的颜色。

### 同色丢弃

同色丢弃要看手牌数量决定是否保留。

```txt
handCount >= 10：同色丢弃组合 +160
handCount >= 7 且能丢 >= 3 张：+220
handCount <= 4 且不能直接赢：-180
handCount <= 3 且只能丢 2 张：-260
能直接获胜或进入 UNO：取消保留扣分
```

附带牌选择顺序：

1. 普通数字牌。
2. 低价值有色技能牌。
3. 尽量保留禁、罚抽、`+6`、`+10`。
4. 如果能直接获胜，可以牺牲高价值牌。

### 对子和顺子

对子：

1. 同色同数字，2 张或更多。
2. 优先张数更多的组合。
3. 多个候选张数相同时，选择打完后颜色优势更高的组合。

顺子：

1. 至少 5 张数字牌。
2. 优先最长顺子。
3. 手牌很多时倾向最长顺子。
4. 手牌少时避免拆掉后续关键组合，除非能获胜或进入 UNO。

### 黑牌保留成本

默认保留成本：

```txt
变色：80
罚抽：150
黑色反转 +4：280
+6：460
+10：560
```

取消或降低保留成本的情况：

1. 没有当前颜色可出。
2. 打出后直接获胜。
3. 打出后进入 UNO。
4. 下家手牌 <= 2。
5. 正在加牌链中。
6. 自己手牌 >= 15。

## 特殊状态处理

### 无合法出牌

没有合法候选出牌时发送：

```txt
draw-card
```

### 刚摸牌决策

如果摸牌后出现 `normalDrawOffer`：

1. 能获胜，立即打出。
2. 能进入 UNO，优先打出。
3. 是 `+6` 或 `+10` 且局势不危险，倾向保留。
4. 评分高于保留成本，打出。
5. 否则 `keep-drawn-card`。

### 加牌链

如果 `drawStack.active === true`：

1. 只生成合法叠加加牌牌。
2. 叠加收益按当前累计摸牌数计算：

```txt
少摸牌收益 = drawStack.amount * 55
```

3. 没有合法叠加牌时发送 `resolve-draw-stack`。
4. `+10` 可以被保留，但当累计惩罚很高时应打出防守。

### 罚抽压力

如果 `drawUntilColor.active === true`：

1. 有罚抽牌则评估打出。
2. 无罚抽牌则发送 `resolve-draw-until-color`。
3. 如果不打就会持续罚抽，罚抽牌保留成本应降低。

## 测试计划

### 算法单元测试

1. 机器人优先打能直接获胜的牌。
2. 机器人能选择对子。
3. 机器人能选择顺子。
4. 手牌多时优先使用同色丢弃快速减牌。
5. 手牌少时保留同色丢弃。
6. 有颜色牌可出时不轻易打 `+6` 或 `+10`。
7. 无颜色牌可出时允许用黑牌变色。
8. 下家只剩 1 张时压制牌评分升高。
9. 加牌链中不允许 `+2` 接黑色加牌链。
10. 刚摸到关键牌时能选择保留。

### 服务端测试

1. 房主可以在无质疑等待房间添加机器人。
2. 非房主不能添加机器人。
3. 有质疑模式不能添加机器人。
4. 房间满员不能添加机器人。
5. 对局开始后不能添加机器人。
6. 机器人自动准备。
7. 机器人轮到自己后约 3 秒行动。
8. 局面变化后旧机器人定时器不会重复行动。
9. 机器人剩 1 张时按可注入随机数决定是否喊 UNO。

### 前端测试

1. 无质疑大厅显示“添加机器人”按钮。
2. 有质疑大厅按钮禁用或隐藏。
3. 点击后玩家列表出现机器人。
4. 机器人显示已准备。
5. 对战页机器人座位显示机器人标签。
6. 轮到机器人时显示“思考中...”。

## 验收标准

1. 房主能在无质疑大厅添加机器人。
2. 机器人能补足人数并参与开局。
3. 机器人所有动作由服务端执行。
4. 机器人回合有 3 秒思考延迟。
5. 机器人能合法打出单牌、对子、顺子和同色丢弃。
6. 机器人能处理加牌链、罚抽和刚摸牌窗口。
7. 机器人会根据手牌多少调整减牌和留牌策略。
8. 机器人会保留 `+6`、`+10`，不会一有机会就乱打。
9. 机器人会在下家危险时使用压制牌。
10. 机器人有 20% 概率忘记喊 UNO。

## 风险与注意事项

1. 机器人调度必须防止重复定时器，否则可能连续出多次牌。
2. 机器人算法不能绕过 `applyCommand`，否则会破坏服务端权威。
3. 组合牌候选数量可能较多，需要限制生成规模，避免极端手牌导致计算过慢。
4. `+6`、`+10` 的保留策略不能过强，否则机器人会一直不用黑牌。
5. 机器人加入后，房间最小人数和准备逻辑要兼容真人 + 机器人混合场景。
6. 暂不支持质疑模式，前端和服务端都要做限制，不能只靠按钮隐藏。
