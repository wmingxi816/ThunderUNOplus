# 雷霆UNOplus 项目开发文档

## 文档用途

这份文档用于统一说明项目结构、目录职责、核心对象、关键方法和整体实现思路。

如果存在不明白的用法、文件职责不清、或者不确定某个模块应该去哪里修改，建议优先查阅本文件。

## 一、项目总体定位

本项目是一个基于 `pnpm workspace + TypeScript` 的 UNO 多端工程，当前重点已经落在以下几层：

- `packages/shared-types`：跨端共享领域模型与类型定义。
- `packages/protocol`：客户端与服务端通信协议定义。
- `packages/uno-core`：UNO 规则核心、牌堆、开局、快照裁剪、对局 reducer。
- `apps/game-server`：内存态房间服务、连接注册、命令分发、WebSocket 网关。
- `tools/simulator`：本地自动对局模拟器、规则自检与批量统计工具。
- `apps/client-wechat`：微信小游戏客户端基础骨架，当前已经包含 WebSocket 接线、本地 store、场景视图模型，以及可直接绑定到 Cocos 节点的控制器层。

项目整体遵循的核心原则：

- 服务端是权威状态源。
- 客户端不能自行判定规则合法性。
- 所有规则判断都集中在 `packages/uno-core`。
- 所有跨端消息格式都集中在 `packages/protocol`。
- 所有跨端共享数据结构都集中在 `packages/shared-types`。

## 三、每个目录里有什么、有什么用

### 1. 根目录

- `package.json`
  作用：monorepo 根包配置，提供 `build`、`typecheck`、`test` 等统一命令。
- `pnpm-workspace.yaml`
  作用：声明工作区，让 `apps/`、`packages/`、`tools/` 作为一个仓库协同开发。
- `tsconfig.base.json`
  作用：全仓库共享 TypeScript 基础编译配置。
- `tsconfig.json`
  作用：根级 TypeScript 配置入口。
- `README.md`
  作用：项目简介、阶段概览、目录概览。
- `GAME-RULES.md`
  作用：游戏规则来源文档，是规则实现的业务背景说明。
- `CARD-CONFIG.md`
  作用：牌组构成来源文档，是牌堆实现的配置依据。
- `next-step.md`
  作用：当前开发阶段说明、下一步开发建议和可直接继续使用的提示词。

### 2. `docs/`

- 存放项目阶段文档、协议说明、状态机说明。
- `PHASE1-SCAFFOLD-1.0.1.md`

- `PHASE2A-UNO-CORE-2.0.0.md`
  作用：记录牌模型、牌堆、规则基础和开局初始化。
- `PHASE2B-UNO-CORE-2.1.0.md`
  作用：记录对局 reducer 和命令处理能力。
- `PHASE2C-PROTOCOL-AND-VIEW-2.2.0.md`
  作用：记录共享类型、协议封口、玩家视角快照。
- `PHASE2D-CLI-SIMULATOR-2.3.0.md`
  作用：记录模拟器与 invariant 校验。
- `PHASE3A-GAME-SERVER-2.4.0.md`
  作用：记录内存态游戏服务器设计。
- `PHASE3B-WS-GATEWAY-2.5.0.md`

- `PROTOCOL.md`

- `项目开发文档.md`
  作用：当前这份总览文档，集中回答“这个项目是怎么组织的、对象和方法都有哪些、改哪里”的问题。

### 3. `apps/`

- 作用：放真正可运行的应用端。

#### `apps/client-wechat/`

- 作用：微信小游戏客户端的 Phase 4A 基础骨架，当前以纯 TypeScript 方式实现网络层、本地状态和场景逻辑，不直接耦合复杂 Cocos UI。
- `project.config.json`
  作用：微信小游戏项目占位配置。
- `game.json`
  作用：小游戏基础运行配置，占位支持横屏和网络超时设置。
- `src/index.ts`
  内容：导出客户端骨架全部入口，并保留 `WechatClientBootstrapPlan`、`ClientRuntimeContracts`、`CLIENT_BOOTSTRAP_PLAN`。
  用途：统一暴露客户端模块，明确当前运行环境仍是微信小游戏 + Cocos Creator。
- `src/app/`
  作用：客户端应用组装层。
- `src/network/`
  作用：WebSocket 通信、请求 ID、消息组装、服务端消息路由。
- `src/store/`
  作用：保存开发态身份、房间快照、玩家视角对局快照。
- `src/scenes/`
  作用：Login / Lobby / Room / Battle 四个基础场景的视图模型骨架。
- `src/cocos/`
  作用：Cocos-ready 的控制器、节点 binding 和 view model 适配层。
- `src/components/`
  作用：卡牌、手牌区、玩家座位、按钮、颜色选择器等基础组件逻辑。
- `src/ui/`
  作用：Toast、LoadingMask、ConfirmDialog 等通用 UI 状态对象。
- `src/utils/`
  作用：卡牌中文显示、动态座位布局、`assertNever`。
- `src/typecheck/`
  作用：存放只参与 TypeScript 校验、不参与运行时的边界测试。
- `package.json`
  作用：客户端应用包定义，当前提供 `build`、`typecheck`、`test`。
- `tsconfig.json`
  作用：客户端 TypeScript 配置。

#### `apps/game-server/`

- 作用：当前最核心的服务端应用，负责房间、连接、消息、广播和 WebSocket 网关。
- `src/main.ts`
  内容：`createInMemoryGameServer()`
  用途：组装 `ConnectionRegistry` 与 `RoomManager`，形成最小可运行的内存态服务端。
- `src/index.ts`
  内容：对外统一导出服务端能力。
  用途：作为包入口，避免外部直接引用内部深层路径。

##### `apps/game-server/src/broadcast/`

- 作用：把服务端内部状态转换成可以发送给客户端的消息。
- `createRoomSnapshot.ts`
  内容：房间快照裁剪逻辑。
  用途：把 `RoomRuntime` 转成对客户端可见的 `PlayerRoomSnapshot`。
- `broadcastRoomState.ts`
  内容：房间状态广播。
  用途：向房间内玩家广播 lobby / playing / settled 阶段的房间视图。
- `broadcastEvents.ts`
  内容：事件广播与事件消息封装。
  用途：把 `GameEvent[]` 打包成协议消息并发给房间玩家。
- `sendSnapshotsToRoom.ts`
  内容：对局中逐玩家发送裁剪后的游戏快照。
  用途：保证每个玩家只能看到自己的手牌。

##### `apps/game-server/src/connection/`

- 作用：维护“连接对象”抽象和连接注册表。
- `connectionTypes.ts`
  内容：`ServerConnection`、`MockServerConnection`。
  用途：定义服务端连接适配层统一接口。
- `mockConnection.ts`
  内容：测试用连接对象工厂。
  用途：用于单元测试和不接真实网络时的模拟发送。
- `connectionRegistry.ts`
  内容：连接注册表类。
  用途：负责注册连接、绑定玩家、按玩家或房间发送消息。

##### `apps/game-server/src/dev/`

- 作用：本地开发调试辅助。
- `runLocalServer.ts`
  用途：启动本地 WebSocket 服务。
- `devClient.ts`
  用途：本地测试客户端，快速手动验证 ping、建房、进房等流程。
- `devWsClient.ts`
  用途：Phase 3C 的真实假客户端封装，供测试和场景脚本复用。
- `scenarioDecision.ts`
  用途：只基于玩家快照做本地决策，不访问完整服务端状态。
- `scenarioRandom.ts`
  用途：提供带 seed 的轻量随机数，保证联调脚本可复现。
- `scenarioTypes.ts`
  用途：定义多客户端联调脚本的参数、结果和内部结构。
- `multiClientScenario.ts`
  用途：运行本地多客户端 WebSocket 联调场景，也是 `dev:scenario` CLI 入口。

##### `apps/game-server/src/dispatch/`

- 作用：命令分发层。
- `dispatchCommand.ts`
  内容：服务端命令入口。
  用途：做房间校验、玩家身份校验，调用 `uno-core.applyCommand()`，再广播事件和快照。

##### `apps/game-server/src/errors/`

- 作用：定义服务端错误码与错误包装。
- `serverErrors.ts`
  内容：`GameServerError`、错误码、错误消息封装。
  用途：统一返回服务端错误给客户端。

##### `apps/game-server/src/gateway/`

- 作用：WebSocket 网关层，只做消息解析、路由、连接生命周期管理，不重写游戏规则。
- `wsServer.ts`
  用途：启动 `ws` 服务端并接入消息、关闭、错误监听。
- `wsConnection.ts`
  用途：把原始 `WebSocket` 包装成符合 `ServerConnection` 接口的连接对象。
- `parseMessage.ts`
  用途：把客户端原始 JSON 解析成强类型消息，并做协议版本与字段校验。
- `messageHandler.ts`
  用途：按消息类型分发到建房、进房、开局、离房、重连、命令处理流程。
- `heartbeat.ts`
  用途：处理 `ping/pong` 心跳。
- `lifecycle.ts`
  用途：处理连接断开后的注销、离房和状态广播。

##### `apps/game-server/src/ids/`

- 作用：集中生成 ID。
- `createRoomId.ts`
  用途：生成六位房间号。
- `createPlayerId.ts`
  用途：生成玩家 ID。
- `createConnectionId.ts`
  用途：生成连接 ID。
- `createRequestId.ts`
  用途：生成请求 ID。

##### `apps/game-server/src/room/`

- 作用：定义房间运行时对象和房间管理器。
- `roomTypes.ts`
  内容：房间运行时状态、玩家、入参、返回值类型。
  用途：作为服务端房间域模型。
- `roomManager.ts`
  内容：`RoomManager` 类。
  用途：负责房间创建、加入、离开、开局、重连和房间列表维护。

##### `apps/game-server/src/tests/`

- 作用：服务端测试。
- `testUtils.ts`
  用途：构造测试服务器、mock 连接、房间 fixture。

- `connectionRegistry.test.ts`

## 四、核心自定义对象、数据结构与方法总览

这一部分按“数据结构 -> 核心类 -> 规则方法 -> 服务端方法 -> 模拟器方法”的顺序说明。

### 1. `packages/shared-types`：共享领域对象

#### `common.ts`

- `UnixMs`
  作用：统一毫秒时间戳类型。
- `RoomId`、`RoomCode`、`GameId`、`PlayerId`、`CardId`、`RequestId`、`EventId`
  作用：统一各种标识符语义。
- `ShuffleSeed`
  作用：洗牌种子类型。
- `GAME_MODES` / `GameMode`
  作用：定义 `with-challenge`、`no-challenge` 两种模式。
- `ROOM_STATUSES` / `RoomStatus`
  作用：定义房间在客户端视角中的 `lobby`、`playing`、`settled` 等状态。
- `GAME_STATUSES` / `GameStatus`

- `registerConnection(connection)`
  功能：注册新连接。
- `unregisterConnection(connectionId)`
  功能：注销连接，并清理玩家映射。
- `bindPlayer(connectionId, roomId, playerId, userId)`
  功能：把连接绑定到玩家和房间。

- `sendToPlayer(playerId, message)`

- `ServerRoomPlayer`
  作用：服务端房间玩家对象。

  逻辑：包含运行中的 `gameState`、快照版本和房间级管理信息。

- `ReconnectPlayerParams` / `ReconnectPlayerResult`
  作用：重连入参与返回结构。

#### `room/roomManager.ts`

- `RoomManager`
  作用：服务端房间生命周期核心类。
  总逻辑：只负责房间和玩家组织，不负责具体出牌规则，真正规则交给 `uno-core`。

- `createRoom(params)`
  功能：创建房间并设置房主。
  逻辑：校验连接存在，生成房间号和房主玩家，初始化 `waiting` 房间，并绑定连接。
- `joinRoom(params)`
  功能：加入等待中的房间。
  逻辑：支持新玩家加入，也支持同一 `userId` 在等待阶段直接复用旧玩家身份重连。
- `leaveRoom(params)`
  功能：玩家离房。
  逻辑：如果房间还在等待中，直接删玩家并重排座位；如果正在游戏中，只标记断线，不删除玩家，给重连留恢复点。

## 五、当前项目的关键实现逻辑

### 1. 对局推进主链路

客户端发出 `command` -> `game-server` 的 `messageHandler` 收到消息 -> `dispatchCommand()` 做房间和身份检查 -> `uno-core.applyCommand()` 执行真正规则 -> 产出新的 `GameState` 和 `GameEvent[]` -> 服务端广播事件 -> 服务端按玩家裁剪并发送快照。

### 2. 房间与连接主链路

WebSocket 建立后，服务端先创建 `ServerConnection/WsConnection` 并注册到 `ConnectionRegistry`。

随后：

- 建房时，`RoomManager.createRoom()` 生成房间和房主。
- 进房时，`RoomManager.joinRoom()` 负责新玩家入座或同一用户重连复用。
- 开局时，`RoomManager.startGame()` 调用 `createInitialGame()` 生成完整局面。
- 断线时，`handleConnectionClosed()` + `RoomManager.leaveRoom()` 共同处理断连或离房。
- 重连时，`RoomManager.reconnectPlayer()` 复用原玩家身份和座位。

### 3. 数据安全边界

项目里最重要的安全边界有两个：

- `createPlayerGameSnapshot()`：确保客户端看不到别人的手牌。
- `createRoomSnapshot()`：确保客户端看不到服务端内部连接信息和其他运行时细节。

同时，`ChallengeWindowState` 中的 `hadBlackCardBeforeDraw` 只允许存在于服务端完整状态中，不允许出现在快照里。

### 4. 模拟器的价值

模拟器不是演示工具，而是规则稳定性工具。

它的主要用途有三种：

- 大量重复跑局，尽早发现规则死锁。
- 每步检查 invariant，尽早发现状态污染。
- 借助种子复现，把偶发 bug 变成可重复调试的 bug。

### 5. Phase 3C 联调工具的价值

多客户端联调脚本不是替代 UI，而是替代“人工点很多窗口”的重复劳动。

它的价值主要有三种：

- 用真实 WebSocket 验证房间、消息、事件、快照、重连整条链路。
- 在不写 Cocos UI 的前提下，提前暴露服务端联机问题。
- 为后续客户端开发提供一个稳定、可复现的联调基线。

### 6. Phase 4A 客户端骨架的价值

Phase 4A 的客户端骨架不是最终 UI，而是把“可点击界面”和“真实服务端链路”之间的边界提前稳定下来。

它的价值主要有四种：

- 让客户端明确只保存 `PlayerGameSnapshot`，不保存完整 `GameState`。
- 让建房、进房、开局、出牌、摸牌、UNO 等操作都统一走 `packages/protocol`。
- 让后续 Cocos 挂节点时，可以直接复用 `App / Scene / Store / MessageRouter` 这一层。
- 在还没接正式美术前，就先把真实联机交互用 TypeScript 层压稳。

### 7. Phase 4B 控制器层的价值

Phase 4B 解决的是“逻辑已经有了，但怎么真正挂到 Creator 节点上”的问题。

它的价值主要有三种：

- 把 `Scene` 逻辑和具体 Cocos 节点解耦，后面换 prefab 或改节点结构时不会反复改业务逻辑。
- 把 `CardView / HandArea / PlayerSeat` 这些组件做成可绑定真实节点的适配层，便于逐步替换成正式 UI。
- 在没有直接依赖 `cc` 运行时的情况下，仍然能把点击和渲染链路用纯 TypeScript 测试压稳。

## 六、开发时应该优先查哪里

- 看规则是否合法：先查 `packages/uno-core/src/rules/` 和 `packages/uno-core/src/reducer/`。
- 看某个命令是怎么执行的：先查 `packages/shared-types/src/command.ts`，再查 `packages/uno-core/src/reducer/applyCommand.ts`。
- 看客户端收发什么消息：查 `packages/protocol/src/messages.ts`。
- 看房间怎么建、怎么进、怎么重连：查 `apps/game-server/src/room/roomManager.ts`。
- 看消息是怎么从 WebSocket 进到规则层的：查 `apps/game-server/src/gateway/messageHandler.ts` 和 `apps/game-server/src/dispatch/dispatchCommand.ts`。
- 看多客户端联调脚本怎么跑：查 `apps/game-server/src/dev/multiClientScenario.ts` 和 `apps/game-server/src/dev/devWsClient.ts`。
- 看客户端 WebSocket 是怎么接协议的：查 `apps/client-wechat/src/network/wsClient.ts` 和 `apps/client-wechat/src/network/messageRouter.ts`。
- 看客户端点击动作最终会发什么消息：查 `apps/client-wechat/src/network/clientMessages.ts` 和 `apps/client-wechat/src/app/App.ts`。
- 看客户端怎么从快照构建对局界面：查 `apps/client-wechat/src/scenes/BattleScene/BattleScene.ts`。
- 看客户端怎么把逻辑挂到 Cocos 节点：查 `apps/client-wechat/src/cocos/controllers/` 和 `apps/client-wechat/src/cocos/bindings/`。
- 看为什么快照里看不到某些字段：查 `packages/uno-core/src/view/createPlayerGameSnapshot.ts` 和 `apps/game-server/src/broadcast/createRoomSnapshot.ts`。
- 看规则是不是被破坏了：查 `tools/simulator/src/invariant/validateGameStateInvariant.ts`。

## 七、维护建议

- 新增规则时，优先修改 `shared-types` 的命令/事件定义，再改 `uno-core`。
- 新增网络消息时，优先修改 `packages/protocol`，不要在 `apps/game-server` 私自定义新消息格式。
- 新增服务端流程时，尽量沿用 `RoomManager -> dispatch -> broadcast` 分层，不要把规则写进 WebSocket 层。
- 新增联调脚本行为时，继续只用 `ClientMessage / ServerMessage`，不要在脚本里直调 `RoomManager` 或 `uno-core`。
- 任何可能暴露隐藏信息的字段，都必须经过 snapshot 裁剪后再发给客户端。
- 修改规则后，优先跑 `uno-core` 测试和 `tools/simulator` 测试。
- 修改联机流程后，额外跑 `apps/game-server` 的 `devWsClient` 和 `multiClientScenario` 集成测试。
- 修改客户端骨架后，至少跑 `apps/client-wechat` 的 `typecheck` 和 `test`。
- 修改 Cocos 控制器或 binding 后，额外检查 `createBattleViewModel`、`controllers.test.ts` 这两层是否仍然通过。
