Phase 6：无质疑模式贪心机器人设计

阶段目标

Phase 6 的目标是在《雷霆 UNOplus》中加入服务端控制的自动出牌机器人。机器人用于补足人数、方便本地试玩和演示，也为后续公开试玩降低组局门槛。

本阶段先完成机器人系统设计，后续实现时必须保持现有架构边界：

  1. 服务端仍然是唯一权威状态。
  2. uno-core 仍然是唯一规则归属地。
  3. 前端只负责大厅按钮、机器人标签和对战展示，不负责替机器人判断合法出牌。
  4. 机器人只能读取自己的手牌、公开牌桌状态、其他玩家手牌数量和公开事件，不能读取真人玩家手牌。

功能范围

第一版机器人只支持无质疑模式：

mode === "no-challenge"

支持内容：

  1. 房主在大厅添加机器人。
  2. 机器人自动加入等待房间并占用座位。
  3. 机器人自动准备。
  4. 满足 3 人开局要求后，房主可以开始游戏。
  5. 轮到机器人时，机器人等待 3 秒后自动行动。
  6. 机器人能自动出单牌、对子、顺子、同色丢弃、黑牌、加牌牌。
  7. 机器人能处理摸牌、刚摸牌是否打出、加牌链结算、罚抽结算。
  8. 机器人剩 1 张牌时有 80% 概率喊 UNO，20% 概率忘记喊 UNO。

暂不支持：

  1. 有质疑模式机器人。
  2. 机器人主动质疑。
  3. 机器人难度等级。
  4. 机器人聊天、表情或个性化头像。
  5. 开局后继续添加机器人。

总体架构

机器人应作为 apps/game-server 内部能力实现，而不是模拟一个浏览器客户端。

建议新增目录：

apps/game-server/src/bot/
├── botScheduler.ts
├── greedyBot.ts
├── botCandidates.ts
└── botScoring.ts

模块职责：

  1. botScheduler.ts：管理机器人 3 秒思考定时器，避免重复调度。
  2. greedyBot.ts：机器人决策入口，读取当前局面并输出最终动作。
  3. botCandidates.ts：根据 uno-core 合法性规则生成候选动作。
  4. botScoring.ts：对候选动作做贪心评分和排序。

服务端流程：

房主点击添加机器人
客户端发送 add-bot
服务端校验房间和房主权限
RoomManager 创建机器人玩家
广播 room-state
房主开始游戏
任意命令成功后检查当前玩家
如果当前玩家是机器人，设置 3 秒定时器
3 秒后重新读取最新局面
生成候选动作
计算最高分动作
服务端内部执行 GameCommand
广播 events 和 snapshot
继续检查是否轮到机器人

候选动作生成

机器人不直接挑一张牌，而是生成所有候选动作，再评分。

候选动作结构：

interface BotCandidateAction {
  type:
    | "play-single"
    | "play-sequence"
    | "play-multiple"
    | "play-discard-same-color"
    | "draw-card"
    | "resolve-draw-stack"
    | "resolve-draw-until-color"
    | "keep-drawn-card";
  cardId?: string;
  cardIds?: string[];
  declaredColor?: CardColor;
  targetPlayerId?: PlayerId;
  score: number;
  reasons: string[];
}

候选来源：

  1. 所有合法单张出牌。
  2. 所有合法对子或多张同色同数字组合。
  3. 所有合法顺子，至少 5 张数字牌。
  4. 所有合法同色丢弃组合。
  5. 所有合法黑牌及其声明颜色。
  6. 加牌链中的合法叠加牌。
  7. 无法叠加时的 resolve-draw-stack。
  8. 罚抽压力中的罚抽牌或 resolve-draw-until-color。
  9. 无牌可出时的 draw-card。
  10. 刚摸牌窗口中的 play-card 或 keep-drawn-card。

合法性必须复用 uno-core：

  1. 单张出牌用 canPlayCard。
  2. 加牌链用 canStackDrawCard。
  3. 顺子、对子、同色丢弃用 uno-core 现有组合规则或抽出的共享判断。
  4. 最终执行仍由 applyCommand 校验一次。

贪心评分模型

机器人使用贪心算法：只评估当前局面，不做多层搜索。

总分可以理解为：

总分 =
  减牌分
+ 威胁压制分
+ 颜色控制分
+ 特殊收益分
- 关键牌保留成本
- 风险成本

减牌分

出牌数量 * 100

示例：

  1. 单张：+100。
  2. 对子两张：+200。
  3. 顺子五张：+500。
  4. 同色丢弃带出四张：+400。

手牌压力

手牌越多越要积极减牌。

handCount >= 15：组合出牌额外 +120
handCount >= 10：组合出牌额外 +70
handCount <= 4：关键牌保留成本提高

胜利和 UNO

出完所有手牌：+10000
出牌后剩 1 张：+1200
出牌后剩 2 张：+350

出牌后剩 1 张时：

80% 发送 say-uno
20% 不发送 say-uno

随机数需要可注入，方便测试稳定复现。

下家威胁

当前方向上的下家越接近胜利，压制牌越值钱。

下家 handCount == 1：禁 / 加牌 / 罚抽 / 有利反转 +500
下家 handCount == 2：禁 / 加牌 / 罚抽 / 有利反转 +300
下家 handCount <= 4：压制牌 +150

反转需要额外判断方向收益：

反转能避开低手牌下家：+250
反转会让低手牌上家更快行动：-250

加牌压力

基础压制分：

普通 +2：+120
普通 +4：+180
黑色反转 +4：+260
变色 +6：+420
变色 +10：+700

保留策略：

有当前颜色可出且下家不危险：+6 额外 -220
有当前颜色可出且下家不危险：+10 额外 -360
没有当前颜色可出：取消 +6 / +10 保留扣分
下家 handCount <= 2：取消 +6 / +10 保留扣分并加威胁压制分
正在加牌链中且不打会摸很多：取消高价值黑牌保留扣分

颜色控制

机器人应该尽量把颜色切到自己的优势色。

颜色评分：

该颜色手牌数量 * 40
该颜色对子潜力 * 30
该颜色顺子潜力 * 40
该颜色技能牌数量 * 20
当前颜色额外 +20

黑牌声明颜色时，选择颜色评分最高的颜色。

同色丢弃

同色丢弃要看手牌数量决定是否保留。

handCount >= 10：同色丢弃组合 +160
handCount >= 7 且能丢 >= 3 张：+220
handCount <= 4 且不能直接赢：-180
handCount <= 3 且只能丢 2 张：-260
能直接获胜或进入 UNO：取消保留扣分

附带牌选择顺序：

  1. 普通数字牌。
  2. 低价值有色技能牌。
  3. 尽量保留禁、罚抽、+6、+10。
  4. 如果能直接获胜，可以牺牲高价值牌。

对子和顺子

对子：

  1. 同色同数字，2 张或更多。
  2. 优先张数更多的组合。
  3. 多个候选张数相同时，选择打完后颜色优势更高的组合。

顺子：

  1. 至少 5 张数字牌。
  2. 优先最长顺子。
  3. 手牌很多时倾向最长顺子。
  4. 手牌少时避免拆掉后续关键组合，除非能获胜或进入 UNO。

黑牌保留成本

默认保留成本：

变色：80
罚抽：150
黑色反转 +4：280
+6：460
+10：560

取消或降低保留成本的情况：

  1. 没有当前颜色可出。
  2. 打出后直接获胜。
  3. 打出后进入 UNO。
  4. 下家手牌 <= 2。
  5. 正在加牌链中。
  6. 自己手牌 >= 15。

特殊状态处理

无合法出牌

没有合法候选出牌时发送：

draw-card

刚摸牌决策

如果摸牌后出现 normalDrawOffer：

  1. 能获胜，立即打出。
  2. 能进入 UNO，优先打出。
  3. 是 +6 或 +10 且局势不危险，倾向保留。
  4. 评分高于保留成本，打出。
  5. 否则 keep-drawn-card。

加牌链

如果 drawStack.active === true：

  1. 只生成合法叠加加牌牌。
  2. 叠加收益按当前累计摸牌数计算：
少摸牌收益 = drawStack.amount * 55
  1. 没有合法叠加牌时发送 resolve-draw-stack。
  2. +10 可以被保留，但当累计惩罚很高时应打出防守。

罚抽压力

如果 drawUntilColor.active === true：

  1. 有罚抽牌则评估打出。
  2. 无罚抽牌则发送 resolve-draw-until-color。
  3. 如果不打就会持续罚抽，罚抽牌保留成本应降低。

Phase 7B：贪心机器人权重可测化与固定手牌调参

阶段目标

Phase 7B 主要围绕服务端贪心机器人 greedy-v1 做算法调参基础设施建设。

本阶段不是新增游戏规则，也不是让机器人绕过 uno-core。目标是把“机器人为什么这样出牌”变得可测、可解释、可重复验证，避免后续靠直觉随意调整分值。

核心目标：

  1. 把机器人评分里的散落数字收敛成命名权重。
  2. 增加三机器人自走测试，用于验证稳定性。
  3. 增加候选权重 A/B 对照，用于判断新权重是否真的更强。
  4. 增加固定手牌场景实验室，用于校准单张牌或某类牌的局部价值。
  5. 根据固定场景结果，优化 +6、+10 的保留策略。

背景问题

Phase 6A 已经设计并实现了服务端贪心机器人。机器人可以生成候选动作，并通过评分选择最高分动作。

但原评分逻辑存在两个调试问题：

  1. 分值直接散落在 botScoring.ts 中，例如 100、1200、-260，很难知道每个数字对应哪个策略意图。
  2. 单纯让三个相同机器人互打，只能测试是否稳定，不能证明某个权重更好。

实际调参需要两类测试：

  1. 整局级测试：多局自走和 A/B 对战，看整体稳定性和胜率。
  2. 局面级测试：固定手牌、固定顶牌、固定下家手牌数，看某张牌是否排在合理位置。

这个场景表示：

5. +6、+10 保留策略优化

固定手牌场景暴露出一个问题：

当机器人已经有红 +2 可以压制下家时，旧权重仍然可能优先打黑色 +6。这会过早消耗高价值黑牌。

本阶段调整：

  1. 提高默认 reserveWildDrawSixCost。
  2. 提高默认 reserveWildDrawTenCost。
  3. 新增 hasPlayablePressureAlternative()。
  4. 如果手里存在可出的有色压制牌，例如禁、反转、+2、普通 +4，就不要因为下家危险而完全免除 +6 / +10 的保留成本。

结果：

红 +2：720 分，排第 1
黑 +6：685 分，排第 2
红禁：600 分，排第 3
红 9：-125 分，排第 4

机器人仍然知道 +6 是强牌，但在已有足够压制手段时，会更倾向于保留它。

核心变更

1. 房主顺移与自动继续

  • 房主显示 重开一把 / 继续游戏。

4. chaos-v1 的核心决策

  • chaos-v1 先复用现有候选生成器拿到所有合法动作，再计算 chaosScore。

  • penalty-draw 针对超大手牌对手。
