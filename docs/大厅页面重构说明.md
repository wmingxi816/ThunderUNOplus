# 大厅页面重构说明

这份文档基于当前代码实现整理，目标是帮助后续重构大厅布局时，快速看清：

- 大厅页面当前由哪些区域组成
- 每个区域承担什么功能
- 数据从哪里来、事件往哪里走
- 哪些逻辑仍然保留，但当前没有对应按钮 UI
- 重构时哪些能力必须接回

主要参考代码：

- `apps/client-web/src/main.ts`
- `apps/client-web/src/styles.css`
- `docs/UI-PART-NAMES.md`

## 1. 当前状态总览

当前大厅已经处于一个特殊阶段：

- 大厅页面的按钮 UI 已全部移除
- 但对应的功能逻辑、消息构造函数、事件绑定函数大多仍然保留在代码中
- 当前大厅更像一个“展示型壳层 + 输入型面板”，而不是完整可操作大厅

这意味着：

- 这份文档要区分“当前页面真实显示出来的内容”和“代码里仍然保留的功能能力”
- 你后续重构时，可以不必重新发明这些功能，只需要决定如何把它们重新接回新的 UI

## 2. 大厅页面的显示条件

大厅不是单独路由，而是由 `render()` 根据状态切换：

- 当 `state.snapshot === null` 时，渲染大厅
- 当 `state.snapshot !== null` 时，渲染对战

也就是说：

- `snapshot` 是大厅 / 对战的总开关

当前大厅渲染入口链路：

1. `render()`
2. `renderLobbyStormBackdrop()`
3. 顶部 `topbar`
4. `renderToastPanel()`
5. `renderLobbyPanel()`
6. `renderRuleModal()`

## 3. 当前大厅的真实结构

当前实际渲染出来的大厅结构如下：

```text
main.shell
├─ lobby-storm-backdrop
├─ section.topbar
│  ├─ div.lobby-title-wrap
│  │  └─ renderLobbyTitle()
│  └─ span.status.status-{connectionStatus}
├─ renderToastPanel()
├─ section.lobby-layout.lobby-layout-v3
│  ├─ div.panel.lobby-control.lobby-control-panel-v2
│  └─ div.panel.lobby-chat-panel
└─ renderRuleModal()
```

重要结论：

- 当前活跃大厅布局是 `lobby-layout-v3`
- 顶部只保留标题和连接状态展示
- 左侧是“组局信息面板”，但按钮 UI 已移除
- 右侧是“房间中枢”，保留成员区、聊天流、聊天输入框
- 规则弹窗逻辑还在，但大厅页面上已经没有规则入口按钮

## 4. 页面分区与组件职责

### 4.1 `topbar`

对应：

- 结构：`render()` 内的 `<section class="topbar">`
- 样式：`.topbar`

职责：

- 展示大厅标题
- 展示当前连接状态

当前组成：

1. `lobby-title-wrap`
   - 内部使用 `renderLobbyTitle()`
   - 负责标题视觉表现
2. `status`
   - 展示 `state.connectionStatus`

当前已移除的顶部按钮 UI：

- `#lobby-music-toggle-button`
- `#lobby-rule-button`

但对应功能逻辑仍保留，见本文第 5 节。

### 4.2 `renderLobbyStormBackdrop()`

对应：

- 结构：`renderLobbyStormBackdrop()`
- 样式：`.lobby-storm-backdrop` 相关类

职责：

- 纯视觉背景层
- 不承担业务交互

包含内容：

- vignette 渐变
- grid 网格
- glow 光晕
- beam 光束
- particle 粒子

如果后续只是重构布局、不改视觉主题，这一层可以独立保留。

### 4.3 `renderLobbyTitle()`

职责：

- 生成大厅标题 `雷霆UNOplus`
- 生成标题粒子和闪电装饰

特点：

- 是一个纯视觉组件
- 不依赖房间业务状态

重构建议：

- 可单独提取成 `LobbyTitleHero`
- 布局重构时优先把它当独立视觉模块处理

### 4.4 左侧主控区：`lobby-control-panel-v2`

对应：

- 结构：`renderLobbyPanel()` 左列
- 样式：`.lobby-control-panel-v2`

职责：

- 承载大厅基础信息输入
- 展示房间摘要
- 为未来重新接回组局操作提供稳定结构

当前实际内容如下。

#### 4.4.1 面板标题区

结构：

- `.lobby-panel-heading`

展示内容：

- 标题：`组局大厅`
- 右侧摘要：
  - 未进房时显示“等待连接”
  - 已进房时显示“当前人数 / 上限”

数据来源：

- `state.connectionStatus`
- `state.room`

#### 4.4.2 昵称输入区 `lobby-identity-row`

结构：

- `#nickname`

职责：

- 展示并编辑当前昵称

当前状态：

- 输入框仍在
- 原来的“改名”按钮 UI 已移除

注意：

- 改名逻辑没有删除，仍保留在 `renameCurrentPlayer()`
- 但当前大厅页面没有按钮去触发它

#### 4.4.3 模式选择区

结构：

- `#mode`

职责：

- 选择游戏模式

当前支持：

- `no-challenge`
- `with-challenge`

当前状态：

- 下拉框仍在
- 但“创建房间”按钮 UI 已移除，所以当前页面无法直接发起创建

#### 4.4.4 房间号输入区

结构：

- `renderRoomCodeInputs()`
- 6 个 `.room-code-digit`
- 一个隐藏的 `#room-id-input`

职责：

- 输入或粘贴 6 位房间号

交互细节：

- 只允许数字
- 输入一位后自动跳下一格
- 退格时支持向前回退
- 粘贴时自动分发到 6 格

事件绑定：

- `bindRoomCodeInputs()`

这一块虽然看起来只是输入框，但交互比较完整，后续重构时建议原样保留体验。

#### 4.4.5 错误提示区

结构：

- `#error-line`

职责：

- 展示最近一次大厅相关错误

来源：

- `state.lastError`

#### 4.4.6 房间摘要卡 `lobby-room-summary-card`

职责：

- 展示大厅关键摘要信息

当前三项：

- 房间号
- 房间状态
- 准备情况

这是一个稳定的信息组件，适合保留并在新布局中重用。

### 4.5 右侧房间中枢：`lobby-chat-panel`

对应：

- 结构：`renderLobbyPanel()` 右列
- 样式：`.lobby-chat-panel`

这是当前大厅最接近“房间工作区”的部分。

内部可拆成四层。

#### 4.5.1 顶部摘要 `lobby-chat-topbar`

职责：

- 快速展示房间级摘要信息

展示内容：

- 大号房间号
- 成员数量
- 三个指标芯片：
  - 房间
  - 成员
  - 模式

#### 4.5.2 成员区

逻辑：

- `room === null` 时显示 `renderEmptyLobbyState()`
- `room !== null` 时显示 `renderLobbyMembersPanel(room)`

##### 空状态 `renderEmptyLobbyState()`

职责：

- 在未进入房间时给出占位和引导

展示内容：

- 未进入房间提示
- 引导文案
- 座位占位格

##### 成员面板 `renderLobbyMembersPanel(room)`

职责：

- 展示房间成员列表

单个成员卡包含：

- 头像
- 昵称
- 状态文案
- 房主徽标

状态文案来自：

- `getRoomPlayerReadyLabel()`

会区分：

- 房主
- 机器人
- 已准备 / 未准备
- 离线 / 已离开

当前状态：

- 成员展示正常
- 当前没有踢人按钮 UI

#### 4.5.3 聊天流 `renderLobbyChatFeed(room)`

职责：

- 展示系统消息和玩家聊天

两种消息类型：

1. `system`
   - 进入房间
   - 玩家加入 / 离开
   - 准备变化
   - 离线 / 重连
   - 房间状态变化
2. `player`
   - 玩家发送的大厅聊天消息

数据来源：

- `state.lobbyChatFeed`

#### 4.5.4 聊天输入区 `lobby-chat-composer`

结构：

- `#lobby-chat-input`

职责：

- 输入大厅聊天消息

当前状态：

- 输入框仍在
- “发送”按钮 UI 已移除
- 仍可通过回车触发 `sendLobbyChatMessage()`

这意味着：

- 聊天发送逻辑还在
- 只是显式发送按钮不在当前大厅 UI 中

## 7. 大厅依赖的核心状态

大厅重构时最常用到的状态字段如下。

### 7.1 页面级状态

- `connectionStatus`
  - 顶部连接状态
  - 控制大量大厅能力是否可用
- `lastError`
  - 大厅错误信息
- `uiToast`
  - 顶部临时提示
- `ruleModal`
  - 规则弹窗状态
- `backgroundMusicPercent`
  - 音乐开关状态

### 7.2 房间状态

- `roomId`
- `playerId`
- `room`
- `snapshot`

说明：

- `room` 是大厅房间数据
- `snapshot !== null` 会直接切出大厅，进入对战

### 7.3 表单状态

- `nickname`
- `roomCodeDigits`
- `lobbyChatDraft`

### 7.4 聊天与成员状态

- `lobbyChatFeed`
- `lobbyMembersExpanded`

注意：

- `lobbyMembersExpanded` 当前没有在活跃大厅布局里真正参与显示逻辑，属于疑似遗留状态

## 8. 大厅的数据流

### 8.1 启动阶段

启动时会执行：

1. `render()`
2. `installBackgroundMusicUnlock()`
3. `connectUsingCurrentInputs()`

说明：

- 当前大厅会自动尝试连接服务端
- 不依赖用户先点击“连接”按钮

### 8.2 服务端消息如何驱动大厅

#### `room-state`

这是大厅最重要的服务端消息。

处理内容：

- `syncLobbyRoomFeed(state.room, message.room)`
- 更新 `roomId`
- 更新 `playerId`
- 更新 `room`
- 清空错误
- 把房间号写回 `roomCodeDigits`

作用：

- 驱动成员、摘要、准备状态、房间状态展示

#### `snapshot`

作用：

- 一旦收到对战快照，页面切到对战

#### `lobby-chat`

作用：

- 调用 `receiveLobbyChatMessage()`
- 把玩家聊天追加到 `state.lobbyChatFeed`

#### `error`

作用：

- 更新 `state.lastError`
- 某些错误会触发 `resetRoomContext()`

#### `room-closed`

作用：

- 清空房间上下文
- 回到大厅空状态

## 9. 当前存在的遗留 / 非活跃代码

这部分对重构非常重要，因为它们还在代码里，但不是当前真实页面结构的一部分。

### 9.1 `renderConnectionPanel()` 仍存在，但当前没有挂载

它定义了：

- `#ws-url`
- `#connect-button`
- `#disconnect-button`
- `#ping-button`
- 旧版 `#rename-player-button`

但当前 `render()` 的大厅分支没有调用它。

结论：

- 这些按钮和输入框不是当前大厅的一部分
- 但连接相关逻辑没有删除

### 9.2 `renderRulesGuidePanel()` 仍存在，但当前没有挂载

它代表旧版大厅底部规则区：

- `rules-guide`
- 四个常驻规则入口按钮

当前实际情况：

- 页面上没有这个区块
- 规则能力仍保留在 `ruleModal`

### 9.3 `renderRoomState(room)` 仍存在，但当前主布局不用它

它代表旧版房间状态面板。

当前大厅实际使用的是：

- `renderLobbyMembersPanel(room)`
- `renderLobbyChatFeed(room)`
- 左侧房间摘要卡

所以 `renderRoomState(room)` 属于旧实现残留。

### 9.4 一些绑定仍存在，但当前页面没有对应按钮

例如：

- `bindLobbyPanel()` 仍会尝试绑定建房、入房、复制、离开、开始、加机器人、准备、音乐按钮
- `bindRuleControls()` 仍会尝试绑定大厅规则按钮

这些绑定不会报错，因为都用了可选链，但当前页面上没有对应按钮。

## 13. 推荐的重构顺序

建议按下面顺序推进：

1. 先确定你要恢复哪些按钮入口
2. 再重构 `renderLobbyPanel()` 的 DOM 结构
3. 再把旧功能逐个重新接回新 UI
4. 最后清理遗留函数：
   - `renderConnectionPanel()`
   - `renderRulesGuidePanel()`
   - `renderRoomState()`

这样做的好处是：

- 先看清能力
- 再设计布局
- 最后清理历史债务

## 14. 当前最值得优先清理的技术债

我建议优先关注这些：

1. 当前活跃大厅与旧大厅实现并存，阅读成本很高
2. 页面上已经没有按钮 UI，但逻辑绑定仍然保留在多个函数里
3. `renderConnectionPanel()`、`renderRulesGuidePanel()`、`renderRoomState()` 都是旧方案残留
4. `bindLobbyPanel()` 已经变成“逻辑很多、当前可见入口很少”的状态
5. 一些状态接近半遗留状态，例如 `lobbyMembersExpanded`

## 15. 一句话总结

当前大厅已经不是“完整可操作大厅”，而是：

- 顶部标题与连接状态
- 左侧信息输入与摘要
- 右侧房间成员与聊天
- 一批功能逻辑仍然保留在代码里，但没有按钮 UI 暴露

如果你接下来要重构大厅，最好的切入方式不是从零做功能，而是先决定：

- 哪些旧按钮能力要恢复
- 放在哪个新区域里
- 继续沿用现有逻辑，还是顺便一起拆组件
